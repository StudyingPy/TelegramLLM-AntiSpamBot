# 指纹复核入口与交互设计

研究日期：2026-10-15。本文是设计建议，尚未改变线上推送或复核流程。

## 结论

推荐使用**独立复核 Bot 的私聊 + Mini App 复核台**：独立会话承载低频提醒，
Mini App 承载证据阅读、筛选和批量操作。现有反广告 Bot 继续发送处理日志。
两个 Bot 可以共用当前审核服务和 SQLite，不需要复制模型扫描、指纹或操作记录。

不增加 Bot 的替代方案是**现有 Bot 的私聊话题 + 同一个 Mini App**。话题能隔离内容，
但不能仅凭 Bot API 文档保证各客户端都有满足需求的独立通知行为，须实机验证。
如果原会话已被整体静音，也不能假设创建话题就会恢复提醒。

无论使用哪个入口，只有 `5439265612` 可接收摘要、读取证据或执行操作。

## 已确认的官方能力

本次通过显式代理下载 Telegram 官方文档。Bot API 页面最新列出的版本为
**10.3，发布日期 2026-08-24**；不能再按旧版“私聊没有话题”“消息只有底部按钮”设计。

| 能力 | 对本项目的意义与限制 | 官方依据 |
| --- | --- | --- |

按钮模型也没有新版 `disabled` 字段。原生富消息方案需要先确认 SDK 升级支持，
或另行实现经过验证的 API 适配，不能直接假设现有代码可用。

## 方案比较

| 方案 | 提醒辨识度 | 批量操作 | 额外成本 | 判断 |
| --- | --- | --- | --- | --- |
| 当前日志私聊再发一条摘要 | 仍会被日志淹没 | 逐条翻页 | 最低 | 不足以解决现有问题 |
| 私聊话题 + 原生富消息 | 内容更清楚；通知效果依赖客户端设置 | 可实现，交互状态较繁琐 | BotFather 开启话题、SDK/API 适配 | 轻量替代 |
| 私聊话题 + Mini App | 内容分流、常驻入口；通知仍需验证 | 良好 | HTTPS 页面与后端 | 不增加 Bot 时采用 |
| 独立复核 Bot + Mini App | 单独会话，用户可独立保留通知 | 良好 | 新 Bot、首次 Start、HTTPS 页面与后端 | 推荐长期方案 |

不推荐把复核详情发进管理群：目前只指定一位复核人，私聊更符合现有权限边界。
Mini App 不是额外的强制通知通道；独立会话也仍然尊重用户的通知设置。

## 提醒与常驻入口

1. 独立复核 Bot 只向固定 ID 发送指纹复核相关消息。创建后需复核人先 Start，
   并由复核人在客户端保留该会话的通知。Bot 不能替用户强制开启通知。
2. 置顶一个常驻面板：待复核总数、有人工误判证据的数量、最久等待时间、
   扫描进度、最近扫描错误。面板提供“打开复核台”和原生 `/fingerprints` 备用入口。
3. 新候选产生或人工处理后更新面板；正常进度更新只编辑面板。
   扫描失败单独显示运行状态，不能伪装成“扫描完成且没有建议”。
4. 沿用每 24 小时最多一条、有新增候选才发送的摘要。标题直接写任务数量，
   例如“待复核 18 条，其中 4 条有人工误判证据”，附一个“开始复核”按钮。
   按钮直接打开 Mini App，省掉当前深链触发 `/start` 后再找列表的步骤。
5. 面板和队列可边扫描边更新，不必等整轮最多 1,000 条全部完成后才可查看。
   1,000 条是模型扫描上限，不是管理员需要处理的建议数量。
6. 保留原有去重约束：同一未决建议或证据未变化的建议不反复推送。
   默认不新增积压催办；若以后需要，单独定义频率和暂停规则。
7. “发送成功”“打开页面”“人工已处理”分别记录，不能因打开页面就把待办清零。
   通知失败保留待通知状态，面板编辑失败不影响队列或指纹有效状态。

若采用现有 Bot 的话题方案，建议为复核人创建“处理日志”“群消息待人工处理”
和“指纹复核”三个话题；不要把需要管理员决定的投票混入静默日志。
只有验证复核人的实际客户端通知行为后，才能将它视为独立 Bot 的通知替代。

## Mini App 的具体操作

首页默认进入待复核队列，显示总数、当前扫描状态和最近一次刷新时间。
按“有人工误判证据 → 误判次数 → 等待时间”排序；模型置信度作参考，不单独主导排序。
提供待复核、已保留、已停用三个视图，支持搜索短语及按指纹类型筛选。

单条卡片展示：

- 可读原短语或模板、指纹 ID、类型、来源、当前权重和命中次数。
- 人工广告／放行反馈与模型判断分开展示，避免把模型推断当成人工结论。
- 模型停用理由与置信度，紧接最多三条已有正文样本；样本保留截断标记。
- 样本中高亮命中的短语，帮助判断“机器人”等过泛词如何误伤普通对话。
- 固定在视野内的“停用并下一条”“保留并下一条”“稍后处理”。
  “稍后处理”只影响工作队列顺序，不改变指纹有效状态。

长证据可展开查看，手机采用单卡阅读，桌面可左右对照列表与详情。
完成一条后自动进入下一条，保留筛选条件与阅读位置，不连续发送聊天消息。
已停用视图展示操作人、时间、原因，并提供显式“恢复”。

批量操作只处理用户勾选的项目，不默认勾选、不提供按模型置信度一键全部停用。
批量提交前展示准确数量和短语清单；提交后逐项报告成功、已处理或证据已变化。
指纹状态或证据版本已变化的项目跳过并提示，防止旧页面覆盖最新结论。

## 服务与权限设计

- 继续由现有扫描任务写入建议，Mini App 通过同一个业务服务读取和处理。
  原生按钮与 Mini App 统一调用复核操作，保留事务、操作记录和禁用后禁止自动重学。
- 所有读写接口都校验服务端身份，严格限制 `user.id == 5439265612`；
  隐藏入口不是访问控制。其他人即使转发链接，也看不到队列、统计或证据。
- 使用菜单按钮或私聊内联 `web_app` 按钮启动，校验签名及 `auth_date` 后建立短期会话。
  菜单模式通过 HTTPS 后端提交操作，不依赖 `sendData`：后者只适用于键盘按钮启动，
  会发送服务消息并关闭 Mini App，不适合连续复核。
- 新 Bot 只增加入口凭据，不增加其他可操作人。后端明确绑定允许的 Bot 与校验密钥，
  Bot token 不进入前端。每次读取、停用、保留、恢复都重新检查服务端权限。
- 操作包含唯一请求 ID 及建议／证据版本；数据库逐项进行条件更新并记录结果。
  双击、网络重试、旧原生按钮和新页面并发操作只能产生一次有效变更。
- 样本以纯文本渲染；继续使用已有的最多三条、每条最多 800 字证据，不为界面
  额外采集个人频道或保存完整聊天。模型建议仍不能直接执行停用。
- 生产需要公开 HTTPS 页面与受认证后端，可部署在现有 VPS。现有 Bot polling
  可以保留，Mini App 的 HTTPS API 不要求把消息接收方式改成 webhook。

## 实施与验收顺序

1. 明确入口方式并完成 BotFather 配置；推荐独立 Bot，先由指定复核人 Start。
2. 建立统一复核服务接口、证据版本检查与幂等提交，再连接 Mini App。
3. 增加独立摘要、常驻菜单、面板 message_id 持久化和面板恢复；旧入口保留备用。
4. 用指定复核人的手机与桌面客户端实测入口、通知、主题、长样本和连续处理。
5. 验证其他 ID 无法读写、旧页面不覆盖新证据、重复提交不重复执行、网络重试和
   批量部分成功可解释，以及禁用不能被重学、恢复可用。
6. 验证摘要仍满足 24 小时与证据去重约束，通知故障不改变指纹状态，再上线。

本文尚未新建 Bot、发送通知、配置 Mini App 或修改生产代码。
