# 视觉广告识别方案与样例验证

状态：2026-11-15，已完成接口核查与本地样例分析；本文件描述待实现的链路，不代表线上已经审核图片。现有文本、重复招揽和抽奖保护继续工作。

## 需要弥补的证据缺口

本次样例覆盖三类绕过：

- 大幅图片内直接招揽赚钱并引导看简介，正文文字接口可能为空。
- 姓名旁的状态图标内含“看我简介”“飞机群发”等文字；单看会员布尔值或图标替代字符会完全丢失其含义。正文甚至可以只有一个数字。
- 消息里显示完整的手续费推广横幅，带金额、产品说明和联系方式。仅凭客户端录屏无法确定它原本是图片、贴纸，还是多个自定义 emoji 拼成的图，需要读取原始消息的实体和附件。

不得用会员身份、美貌头像、动漫头像、文字少或单纯带贴纸作为广告证据。识别的是视觉内容里的招揽、联系方式、导流和收益承诺，以及它们与当前消息的关系。

## Telegram 能提供什么

| 来源 | 接入入口 | 注意事项 |
| --- | --- | --- |
| 最新头像 | `getUserProfilePhotos(user_id, limit=1)`，或 `getChat(user_id).photo` 的可下载图像 | 仅当前头像，不能把结果永久绑定账号。Bot API 的照片接口不保证覆盖用户客户端所见的动态头像视频。 |
| 姓名旁 emoji 状态 | `getChat(user_id).emoji_status_custom_emoji_id`，再调用 `getCustomEmojiStickers` | 普通 `User` 仅有 `is_premium`，并不携带状态图标 ID；支持状态到期时间，不能复用当前七天 Bio 缓存。 |
| 正文、说明里的自定义 emoji | 原始 `entities` / `caption_entities` 中 `type=custom_emoji`、`custom_emoji_id` | `offset`、`length` 是 UTF-16 code units；必须保留原始文字、数字、换行和实体位置，不能先用现有去数字/emoji 的归一化结果重建。 |
| 贴纸 | `Message.sticker` 的文件 ID、格式标记、缩略图、关联 emoji | 关联的普通 emoji 和贴纸包名称不能代替实际画面；静态 WEBP/PNG、动画 TGS、视频 WEBM 都要覆盖。`premium_animation` 是另一项可能需要查看的素材。 |
| 图片、动图、视频 | `Message.photo` / `animation` / `video` | 先支持图片、贴纸和短动画；长视频另设预算，不默默假定已看完整个视频。 |

上述字段在当前本地 aiogram 3.28.2 已存在。资料字段、头像与文件可能不可获取，必须记录 `unavailable`，不得把 API 失败当作干净资料。展示姓名中的任意装饰也不能假定都带有可解析的自定义 emoji ID。

官方依据：

- [ChatFullInfo：头像、状态 emoji 与到期时间](https://core.telegram.org/bots/api#chatfullinfo)
- [MessageEntity：custom_emoji 及 UTF-16 偏移](https://core.telegram.org/bots/api#messageentity)
- [getUserProfilePhotos](https://core.telegram.org/bots/api#getuserprofilephotos)
- [getCustomEmojiStickers](https://core.telegram.org/bots/api#getcustomemojistickers)
- [Sticker：格式、缩略图与需要重着色的图标](https://core.telegram.org/bots/api#sticker)

## 建议的首版审核顺序

1. 保持现有管理员和白名单入口。提取正文及视觉素材清单；新成员、观察期账号、重复招揽、可疑编辑、含自定义 emoji/贴纸/图片的消息优先进入视觉覆盖。
2. 下载有上限的素材并本地渲染：头像一张、状态图标、正文中每个自定义 emoji，以及消息附件。将“头像”“状态图标”“正文附件”等来源明确标注，避免把头像广告误认为正文广告。
3. 自定义 emoji 先按 UTF-16 位置组成文字/素材序列，再渲染组合画布；同时保留单个素材的高清视图。跨行拼图广告不能只逐块 OCR，短数字正文也不能被清洗掉。截图和平台 UI 文字仅用于本轮验证，正式链路从 Telegram 原始对象取材。
4. 正式接管处置的目标链路保留 **Jev 先判断、MiMo 后复核** 的顺序。Jev 接收原始文字、近期行为、资料与视觉素材清单；MiMo 在同一文本上下文之外接收原图/渲染帧。正式链路复用现有 MiMo 复核请求，避免每条消息再加一次独立视觉模型调用。先行影子阶段则保持原有文本审核请求和决定，完成后另在有界队列里调用视觉 MiMo；额外视觉费用按单独样本配额管理，结果只供对照。
5. MiMo 输出广告判断，同时返回结构化视觉证据：来源、可见原文、导流对象、帧范围、模糊/缺失标志。将 `message_is_promotional` 与 `profile_has_advertising` 分开，代码按 `scope=body|profile|unknown` 做处罚门槛。消息图里完整广告可走普通模型阈值；头像/状态广告作为账号资料证据，需与招揽、重复行为或正文信号印证。仅头像或状态可疑时先记录复核；明确的重复导流再考虑投票，不能把模型“此账号看起来像广告”的输出直接变成当前消息的自动封禁。
6. 视觉素材存在但渲染或模型识别失败时，记录“视觉证据未覆盖”。不能把未识别内容缓存成正常，也不能仅凭取图失败投票或封禁。仍有独立正文硬证据的消息保留原有处置；依赖画面的判定不可伪装成完整的双模型复核。

当前 `_feature_payload` / Jev 客户端是 JSON 文本链路；把 `image_url` 或 base64 字符串放进去不代表模型看到了图片。实现时应使用独立、只在内存传递的 `VisualInputs`，由 MiMo 请求构造器产生真正的多模态 `image_url` blocks，不将图片字节塞进特征 metadata 或 Jev 侧库。

两侧输入不再完全对等：记录共享文本 hash、视觉素材 hash，以及 `input_parity=reviewer_has_visual_context`。视觉补充样例与旧版“两个模型看到相同输入”的实验分开统计，不能把 MiMo 因为多看图片得到的差异误算为模型能力胜负。后续可把可靠本地 OCR 结果提供给双方，仍需保留来源与误识别标志。

## 动画、缓存与费用

- TGS 使用独立 rlottie 渲染，WEBM/GIF/短视频使用 ffmpeg。初始取时间分散的 4–6 帧，去除完全相同帧；遇到文字变化再加采样。只取首帧或缩略图会漏掉闪现广告，也不能声称固定采样保证覆盖每一帧。
- 自定义 emoji 可能要求 `needs_repainting`。透明图使用明暗背景检查可读性；避免透明底变黑、文字消失或颜色语义被错误合成。
- 缓存按 `file_unique_id` + 内容 hash + 渲染器/模型/策略版本索引。头像/状态另存当前文件/emoji ID 和短期刷新时间；不要用账号 ID 或 Bio 的七天 TTL 作为素材未变的证明。
- 初始建议：单条素材下载合计 4 MiB、最多 8 个独立素材、最多 12 张渲染图；影子任务独立队列、60 秒总超时、并发 2，不占用主审核的等待预算。均需配置化并记录截断；拼图超出预算应优先保留整幅低分辨率画布，再取重点高清块。四图实测约 47 秒，现有文本审核的 8 秒超时无法直接复用；启用处罚前必须单独测量单消息延迟、队列积压及费用，优化提示词、输出长度、采样和缓存。
- 热门贴纸/emoji 的识别结果可复用，头像不必逐条重做模型调用。首次部署不回扫全群所有历史头像。
- 图片/帧暂存在内存或有时限的缓存。持久日志保留有界 OCR、来源、素材 hash、覆盖状态和最终人工反馈；不保存带 Bot token 的下载地址，也不把 base64 写入 action_log、Jev state、通知或 Git。

## 防误封与验证安排

- 广告素材复制粘贴进举报、引用或玩笑，并不等于发言者主动推广。正文、回复关系、素材来源与群内活动上下文共同判断。
- 普通抽奖口令、管理员活动海报、带品牌头像的正常成员、普通付费状态图标都需要负例覆盖。会员身份本身不加广告权重。
- OCR 和看图模型的结论属于模型证据；图片中的指令、二维码、链接都按不可信数据处理，不自动打开或执行。仅相似图 hash 只能用于候选检索，不能跨账号直接连带封禁。
- 首次上线建议 `VISION_MODE=shadow`：真实采集/识别，记录建议和覆盖率，沿用现有线上处置。初始限定测试群与每天最多50个视觉请求，采样/配额只约束影子任务，不跳过现有文本审核。收集明确的人审正负样本后再启用参与处罚。先覆盖头像/状态/自定义 emoji/贴纸，长视频为后续阶段。
- 单元与集成检查重点：UTF-16（尤其 emoji 占双码元）、换行拼图、TGS/WEBM 多帧、状态更换/到期、缓存失效、模型拒答/超时、媒体缺失、可信活动通知、跨账号素材复用、管理员豁免及存储中没有图片字节/凭据。

## 本轮研究范围

原始截图、录像、抽帧图、官方文档下载与隔离验证输出放在 gitignored 的 `data/vision-research/`。GitHub 只提交通用方案，不上传用户提供的聊天截图或录像。一次样例 API 验证已获得用户明确授权。本轮不修改生产视觉处置逻辑。

## 当前 MiMo 的隔离实测

使用现有 `mimo-v2.6-flash`，一次请求输入本次三张图片和录像首帧，实际返回 HTTP200；供应商返回的 resolved model 同名，usage 含1366个 image tokens，证明本次图片作为图像输入被处理。总计1555输入/1436输出 tokens，其中633 reasoning tokens；耗时46966ms。输出完整 JSON，未执行任何 Telegram 处置或更改线上配置。

| 样例 | 观察到的识别结果 | 需要防范的问题 |
| --- | --- | --- |
| 图片内收益招揽 | 读到高额收益承诺与“看我简介”导流，能识别主要广告语义 | 个别文字识别有遗漏、错字；不能将 OCR 当作逐字真值 |
| 正文招揽 + 状态图标 | 读到正文招揽，也在其他说明字段中读到了图标“看我简介” | `status_icon_text` 却填 unknown，并把发送者姓名填到 `avatar_text`，字段归属不可靠 |
| 正文仅一个数字 + 状态广告 | 读到正文“1”和图标“飞机群发”，称为“间接”广告，并承认正文也可能是签到/占位 | 必须按资料证据处理，不能直接把该条消息判成明确推广；需代码层来源与行为门槛 |
| 录像首帧 | 读到手续费、费率、招募与联系方式，区分内容里的“官方认证”印章和客户端身份状态 | 仍有小字 OCR 错误；截图本身不能证明原始素材属于贴纸、自定义 emoji 或图片 |

结论是现有模型具备图像读取能力，不必先更换供应商；但这只是四个偏广告样例的一次能力验证，不能据此报告准确率、误封率或线上时延分布。下一步的实现重点是原始素材与来源标签、组合渲染、异步影子队列及正常样本评估，而不是单独增加一个“看图后封禁”的判断。
